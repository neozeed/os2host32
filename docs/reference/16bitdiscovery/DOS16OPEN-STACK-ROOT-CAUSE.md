# Dos16Open apparent 26/30-byte frames: root cause

Milestone: Soft386 NE-H3S investigation, 2026-10-08.

## Result

There is one documented 16-bit `DosOpen` ABI here: 26 parameter bytes. The apparent 30-byte calls observed in LIB.EXE, LINK386.EXE and RC.EXE were caused by Soft386 returning from `DOSCALLS.75` (`DosQFileMode`) with the wrong Pascal stack cleanup.

Soft386 had cleanup=8 for ordinal 75. The Microsoft Programmer's Library documents and the Microsoft CRT call site both show 12 bytes:

* far pathname pointer: 4 bytes
* far attribute-output pointer: 4 bytes
* reserved DWORD: 4 bytes

The CRT sequence immediately before some DosOpen create/replace calls invokes DosQFileMode. Leaving its reserved DWORD on the guest stack shifts the later DosOpen pathname/handle/action pointers by exactly four bytes. H3M's 30-byte DosOpen frame heuristic accidentally compensated for this earlier corruption.

## Binary evidence

RC.EXE has one DOSCALLS.70 relocation site in segment 1 at offset D20B. The same Microsoft CRT sequence is present in LINK386.EXE and LIB.EXE. Immediately before the DosOpen import it conditionally invokes a chained DOSCALLS.75 relocation at RC segment 1 offset D1ED. The relevant sequence pushes pathname (4), attribute pointer (4), reserved zero DWORD (4): 12 bytes.

Microsoft Programmer's Library `os2adv.txt`, DosQFileMode, independently specifies:

```
PTR ASCIIZ   Pathname of file
PTR WORD     Receives file attribute
DWORD        Reserved (0)
```

`prgmr4.txt`'s assembly DosOpen example independently confirms the normal DosOpen push order and 26-byte parameter payload.

DosOpen2 is not the explanation: it is a separate DOSCALLS.95 API and has an additional EA pointer / wider open-mode interface.

## H3S correction

* DOSCALLS.75 cleanup: 8 -> 12 bytes.
* DOSCALLS.70: always decode the documented 26-byte ABI; remove 26/30 frame scoring.
* Keep the separately observed Microsoft CRT `0043` create/replace access-mode compatibility case narrow; that value is generated by the CRT and is independent of the four-byte stack leak.
* DOSCALLS.94 (`DosGetPID`) is backed by explicit guest PID/TID/PPID state (initial process 1/thread 1/parent 0), ready to connect to common process/session bookkeeping later.

## Regression evidence

After the correction, `make check-ne` passes including LIB creation and object-addition tests, and `make check-quick` passes including the existing 32-bit LE/thread/synchronization/memory and bridge tests.
